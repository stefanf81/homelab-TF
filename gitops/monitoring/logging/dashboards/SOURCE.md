# Custom Grafana dashboards (logging)

Provisioning model:

- `kustomization.yaml` generates one ConfigMap per dashboard from the JSON file
  next to it (`configMapGenerator`, `disableNameSuffixHash: true`).
- The Grafana sidecar discovers ConfigMaps labeled `grafana_dashboard: "1"` in
  the `monitoring` namespace and reloads Grafana after changes
  (`sidecar.dashboards` in `gitops/monitoring/platform/release.yaml`).
- The `grafana_folder` annotation places each dashboard in a Grafana folder
  (sidecar `folderAnnotation` + `provider.foldersFromFilesStructure`).
- ConfigMap names and dashboard UIDs are stable on purpose: the sidecar adopts
  the existing dashboard instead of creating a duplicate. Do not rename a
  ConfigMap or change a dashboard `uid` without a migration plan.
- Datasource references use template variables (`datasource` for
  VictoriaMetrics, `lokiDatasource` for Loki) so UIDs stay portable.

## Metrics derived from logs

The overview panels of `taskflow-waf.json` and `taskflow-rate-limits.json` read `loki_process_custom_taskflow_waf_*` metrics instead of scanning Loki. They are produced by the metrics-only `loki.process` components `waf_requests` (requests, duration histogram and rate-limit rejections from one parse), `waf_audit` and `waf_rules` in `alloy-release.yaml`, scraped from Alloy by the `alloy` VMServiceScrape. They cover all clients and honor only the Application filter; the Client IP filtered versions stay in Loki (collapsed rows). `tests/validate-alloy-metrics.sh` runs the real Alloy image (v1.21.1, the app version of chart 1.14.1, with `--stability.level=experimental` like the release) over fixture logs and checks every counter and the duration histogram, so change the pipeline and the dashboards together. Detections, rule IDs, rule messages, paranoia tags and inspection latency are read only from Coraza-written parts of an audit record: the top-level `},"messages":[{` array (Coraza `%q`-quotes its own `[id \"N\"]`/`[tag \"…\"]` values, while client data is escaped twice) and `"stopwatch":"…"`. Coraza lowercases request header names into the record, so a bare `"messages"` needle would count a client header `Messages: …` as a detection and let it inject `rule_id` labels; the fixtures include such header-key spoofs. LogQL line filters follow the same rule: a bare quoted word is satisfied by a request header value, so probes are excluded with `!= "\"uri\":\"/waf-healthz\""` (Caddy's `request.uri`, as the Alloy `stage.drop` does) and audit records are selected with `|= "\"transaction\":{"`; `validate-dashboards.rb` rejects the bare forms. The client IP is read from `request.client_ip`, which Caddy writes on every access record (the top-level `client_ip` is missing on `/waf-healthz?…`).

- **Counter semantics:** These counters are created at their first event and start from zero. WAF request, rejection and detection counts use the same bounded hybrid as Kyverno, cert-manager and Spring: `(increase_pure(m[w]) unless last_over_time(m[1h] offset w)) or increase(m[w])`, summed only afterwards. This preserves a new series' first burst while using `increase()` for a series seen in the hour before the window. Request rates divide the same increase by `$__rate_interval_ms / 1000`. Zero fallbacks multiplied by 0 can keep plain `increase_pure()`. This is MetricsQL-specific, not portable PromQL. Missing samples can put the preceding value beyond the engine's lookback; plain `increase_pure()` then treats the retained cumulative value as a first burst. The regression fixture goes from 5000 before a gap to 5001 at recovery and 5003 later: a short gap retains the baseline and returns 3; a longer gap crossing a 5-minute window returns 2 with the hybrid in an instant query instead of 5003, losing the unobservable recovery increment. A range query that loads the older baseline returns 3, so summary cards and charts can differ after gaps. **Limit:** the one-hour guard is a bounded heuristic, not proof of series birth. If no sample exists in that preceding hour (long outage, changed labels, retention boundary), the initial cumulative value can still be counted. Events before collection or during scrape gaps cannot be reconstructed exactly; use the retained Loki records for investigation, not these counts as an exact ledger. Do not apply the formula indiscriminately to counters first collected midway through their lifetime.
- **Coverage:** Metrics started on 2026-10-18 at 13:34 UTC. A range spanning that point can have larger Loki totals than metric totals. The overview row headings state coverage and filter scope explicitly.
- **Missing series:** A zero fallback must be derived from request counters, grouped by application when appropriate. Keep the fallback on the Caddy side of the upstream-429 subtraction: upstream 429s can exist before the first Caddy rejection. Metric panels are gated by a successful Alloy scrape at the evaluation time, so scrape failures are gaps rather than healthy zeros. This does not detect a stalled log source; check pipeline health too. Empty rule panels report no matching detections, not proof of healthy ingestion.
- **Redaction and line size:** Alloy redacts Authorization/Proxy-Authorization/Cookie/Set-Cookie values, query values named like token/password/secret/code/state/session/api_key/jwt, and Coraza matched data of cookie, Authorization, body and credential-named-argument variables on every `job="coraza-waf"` line, and drops the per-message `[uri "…"]` copies from audit records (a 19 KB URI made a 540 KB record, over Loki's 256 KB `max_line_size`). Other headers, parameters and matched data are stored as sent. `tests/validate-alloy-metrics.sh` checks this; see `docs/TASKFLOW_WAF_ARCHITECTURE.md`.
- **Regression tests:** `python3 gitops/images/taskflow-caddy-coraza/tests/validate-waf-dashboard-metrics.py` runs the actual dashboard expressions against a disposable VictoriaMetrics container (Docker required, no cluster writes). Alternatively set `VM_BINARY` to a local VictoriaMetrics executable: the test starts its own loopback-only process with temporary storage, never an external TSDB. Use the deployed stack 0.96.0's VMSingle version (v1.154.0, also the default `VM_IMAGE`). Fixtures cover first bursts, resets, window boundaries, upstream-only 429s, quiet applications, scrape failures, actual missing counter samples, and new-pod restarts across kube-state-metrics replacements; the same gap fixtures cover the Falco rule-match pies and bars and the Logging pipeline discard tile and chart. Gap and restart checks exercise both instant and range queries. The config-validation CI runs it alongside the Loki tests. `tests/validate-dashboards-test.rb` pushes access records whose headers carry `/waf-healthz` and `transaction` and asserts the log panels still count them and the audit series does not.

## Conventions shared by all dashboards

- **Navigation:** every dashboard carries the tag `homelab` and a first link of type `dashboards` (tag `homelab`, shown as the "Dashboards" dropdown). A new dashboard without the tag is missing from every dropdown, so add both. Other tags describe the topic.
- **Shared crosshair:** `graphTooltip: 1`, so hovering one chart marks the same time on all charts.
- **Annotations:** the Taskflow dashboards with a VictoriaMetrics datasource (`taskflow-performance`, `taskflow-waf`, `taskflow-rate-limits`) mark Deployment rollouts (`kube_deployment_status_observed_generation` changes) and container restarts (`kube_pod_container_status_restarts_total` increases) in the `taskflow` namespace. Annotation queries use the literal datasource uid `VictoriaMetrics`: the `${datasource}` variable did not resolve in annotation queries on Grafana 13.2.x. Restarts and rollouts are instance-agnostic (`max by` over the kube-state-metrics series, subquery `[$__interval:30s]`), so a kube-state-metrics replacement is not drawn as an event.
- **IP drill-down:** Client IP columns link to the other Taskflow dashboards with `var-client_ip` filled in and to an AbuseIPDB lookup (opens in a new tab on click). Cloudflare and Cilium drops happen before the WAF, so the Blocked Sources tables link only to the lookup.
- **Refresh:** dashboards that scan Loki refresh every 5 minutes (Blocked Sources: 1 minute, measured at 0.8 MB scanned per load over 24h on lab data); metrics-only dashboards refresh every 30 seconds to 1 minute.

Updating a dashboard:

1. Edit the JSON file (keep the `uid` and the datasource template variables).
2. Run the dashboard validation:
   `LOKI_URL=... ruby gitops/images/taskflow-caddy-coraza/tests/validate-dashboards.rb gitops/monitoring/logging/dashboards/*.json gitops/monitoring/app/dashboards/*.json`
   or the full suite `gitops/images/taskflow-caddy-coraza/tests/validate-configs.sh`
   (requires docker, helm, ruby, python3 and kubectl). The suite also renders both
   Kustomizations with `kubectl kustomize` and fails if a JSON file is not
   provisioned by their `configMapGenerator`s, drifts from its rendered
   ConfigMap, lacks the `grafana_dashboard` label, or has no valid relative
   `grafana_folder` annotation. Run it after adding a dashboard file or
   editing a `kustomization.yaml`.
3. Commit; Flux applies the updated ConfigMap and the sidecar reloads Grafana.
4. After Flux has reconciled, check the live cluster:
   `python3 gitops/monitoring/tests/verify-dashboards-live.py --grafana`
   (needs kubectl; opens temporary port-forwards). It runs every dashboard
   query against VMSingle and Loki with the default variables (ERROR fails,
   EMPTY is reported as "No data right now"), checks the label sources and
   counts the dashboards rely on, and confirms Grafana serves the repo JSON.
   `--spoof-url https://<site>` additionally sends one request with a fake
   WAF `Messages` header and checks that it is not counted as a detection.

For dashboards imported from elsewhere, record the upstream URL/ID and the local
adaptations in this file.
